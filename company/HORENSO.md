# 報連相 規程（2026-07-25 社長指示により制定）

**なぜ作るか**: 第6回監査で、開発部が単独で書いた削除機能が全ファイル消失を起こしうる状態だった。
セキュリティ室のチェックリストに「削除機能」の項目すら無く、誰にも相談されないまま実装・デプロイされた。
**黙って作って事故ってから発覚**を無くすための規程。

---

## 1. 報告（下から上へ・事後）

| 誰が | 誰に | 何を | いつ |
|---|---|---|---|
| 全部署 | 凪 → 社長 | 実装したもの・数字・**失敗したこと** | 作業完了時 |
| 桐生 | 全部署 | 日報（掲載本数・PV・Gemini予算・警報） | 毎便（自動） |
| 鵜飼 | 凪 → 社長 | 監査結果（指摘件数・重大の有無・受容判断） | 監査実施時＋週次 |
| 財津 | 凪 | 経済欄の数字と品質 | 週次 |

**報告の鉄則**: 成功だけを報告しない。**失敗・却下・受容したリスクを必ず併記する**（社訓「嘘偽りなく」）。

## 2. 連絡（横へ・事前と同時）

**着工前に必ず関係部署へ連絡する対象**:

| 作業 | 連絡先 | 理由 |
|---|---|---|
| **削除・上書きを伴う機能** | **鵜飼（必須）** | 第6回事故の再発防止。生成機能と違い既存資産を壊す |
| 外部データを表示する機能 | 鵜飼 | XSS経路が3回発生している |
| 記事の書き方・ルール変更 | 真行寺・揚羽 | 品質基準の一貫性 |
| ソース追加・削除 | 久遠 | 巡回計画と重複判定への影響 |
| 株式・企業欄に関わる変更 | 財津 | 投資助言ガードの範囲 |
| 見た目・導線の変更 | 八重樫・桐生 | 実装とAIO/告知への影響 |
| 課金・公開・鍵に関わること | **社長（必須）** | 後戻りできない |

## 3. 相談（判断を仰ぐ・事前）

**独断で進めてはいけないもの**:
- リスクを「受容する」判断 → 鵜飼に相談し、台帳に理由と見直し条件を記録
- 期待値に関わる報告の書き方 → 凪に相談（盛らない）
- 経営目標・収益化に関わる判断 → 社長に相談（GOALS.mdの梯子を飛ばさない）
- 「これは危ないかも」と少しでも思ったこと → **迷ったら相談する側に倒す**

## 4. 実装への落とし込み（口約束にしない）

| 仕組み | 内容 |
|---|---|
| 着工前チェックリスト | `company/security/RISK_LEDGER.md` 末尾。**削除機能の項を追加済み** |
| 自動報告 | 日報（毎便）・status.json（事務所ライブ）・precheck警報 |
| 相互確認 | 週次定例で各部署が他部署の作業に意見を述べる（相互採点の継続） |
| 記録 | 会議録 `company/meetings/`・提案 `company/proposals/`・監査 `company/security/` |

**規程の実効性**: 報連相を怠って事故が起きた場合、原因分析を議事録に残し、可能なら機械的検知（precheck）に変換する。
